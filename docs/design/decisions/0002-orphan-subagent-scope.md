# 0002: 孤儿子 agent 清理范围(scope ③)

## 状态

accepted(2026-09-07)

## 背景

页面归档的会话由 scope ② 超保留期物理删除,但**归档动作不级联子 agent**:子 agent 目录(每跑一批 StarRail 就新增几个到十几个)既不在 GUI 归档名单里(页面根本不显示),也没有任何自动机制覆盖,只能躺在 `sessions/` 里无限积累。它们全部计入 `session.list` 载荷——2026-09-06 实测 116 条存量里 82 条属于此类;664 条时代 566 条 StarRail 里 492 个是子 agent。这是"批量跑完 → 列表膨胀 → 远程变卡"循环的结构性根源。

## 备选

1. **retention 插件加 scope ③(采纳)**:复用既有清扫调度、mtime 探测、attached 跳过、静默复查、审计清单全套安全设施,只新增"读头部取 parentSession + 父存在性判定"
2. **subagent-cleanup 插件扩展**:该插件是手动触发的工具形态,自动化清扫不是它的职责定位
3. **独立"自动归档"插件**:覆盖面更大(冷主会话也自动归档),但工程量更大,可作为后续项目;scope ③ 先把最疼的子 agent 积压关掉

## 决策

scope ③ 判据(全部满足才删):

1. 目录头部 `parentSession` 指向的会话 id 在 `sessions/` 全 workspace 目录名索引中**不存在**(目录名 = 会话 id)
2. 目录最新写入早于保留期(冷)
3. 不在内存(`ctx.sessions.get` 未命中)
4. 动作前 `stillQuiescent` 复查通过

保守规则:头部读取失败 = 无法确认父子关系 = 永不删除;父目录仍在宽限期内时子目录等待,父物理删除后下一轮跟随;配置项 `cleanOrphanSubagents` 默认开,设置页卡片可关。

## 后果

- 子 agent 积压从"无限增长"变为"跟随父会话的宽限期自动消亡",`session.list` 载荷不再被看不见的目录撑大
- 父子删除最多相差一个清扫周期(同轮或下一轮),家族不会在"父还在时子先消失"
- 判据依赖"目录名 = 会话 id"与头部 `parentSession` 字段的稳定性;上游若改会话目录布局,scope ③ 静默失效(不误删),需随升级核对
